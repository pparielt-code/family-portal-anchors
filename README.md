# family-portal-anchors

Внешний якорь цепочки манифестов журнала целостности «Семейного портала» (ADR-013, шаг 2).

**Назначение — одно.** Сделать **удаление** манифестов заметным. Проверка внутри приложения
(`GET /api/v1/integrity/chain`) читает ту же базу и по построению не может увидеть, что новейшие
манифесты исчезли: остаток согласован сам с собой и получает честный вердикт `COHERENT`. Этот
репозиторий хранит записи о состоянии цепочки в момент импорта — вне прод-хоста, в истории, которую
нельзя переписать.

## Почему отдельный репозиторий, а не ветка в `family-portal`

Проверено, а не предположено: прод-хост умеет пушить в `family-portal`
(`git push origin HEAD:refs/heads/__push-probe` → ветка создана, exit 0). Якорь, лежащий там,
прод может переписать — и весь смысл теряется. Здесь пишет только оператор со своей машины,
а неизменяемость держит GitHub: защита ветки `main` запрещает force-push и удаление, включая
администраторов.

## Почему репозиторий публичный

Не по недосмотру. На бесплатном плане GitHub защита веток **есть только в публичных** репозиториях:
в приватном GitHub отвечает `403 Upgrade to GitHub Pro or make this repository public to enable
this feature`. Проверено, что дело не в правах токена — тот же токен создаёт репозиторий и меняет
его настройки (`PATCH → 200`).

Публичность здесь ничего не раскрывает, потому что раскрывать нечего: в записи только
идентификаторы манифестов, счётчики и метки времени — никакого содержимого журнала, имён, адресов
и текстов (см. «Формат записи»). Видно, **сколько** импортов было и **когда**, но не что в них
записано.

Отвергнутые варианты: приватный репозиторий + GitHub Pro (~4 USD/мес, платёж) и публичное зеркало
хэшей при приватном журнале (два репозитория и лишний шаг публикации — лишняя точка отказа).

## Формат записи

Одна строка `anchors/anchor-log.jsonl` — одна запись, один импорт. Файл **только дописывается**.

```json
{
  "anchorVersion": 1,
  "sequence": 1,
  "manifestIds": ["<id манифеста, появившегося при этом импорте>"],
  "chainLength": 1,
  "rootIds": ["<id корня>"],
  "headIds": ["<id головы>"],
  "verdict": "COHERENT",
  "checkedAt": "2026-11-01T10:00:00.000Z",
  "writtenAt": "2026-11-01T10:03:12.000Z"
}
```

| Поле | Что это | Зачем |
|---|---|---|
| `anchorVersion` | `1` | формат изменится — старые записи должны остаться читаемыми |
| `sequence` | 1, 2, 3… без пропусков | пропуск = запись удалена |
| `manifestIds` | головы, которых не было в предыдущей записи | что именно добавил этот импорт |
| `chainLength` | `manifestCount` на момент записи | **меньше, чем в якоре, — манифесты удалены** |
| `rootIds` | корни цепочки | появление второго корня видно без базы |
| `headIds` | головы цепочки | замена головы при том же счёте — тоже удаление (с добавлением) |
| `verdict` | вердикт сводки | якорь фиксирует только `COHERENT`; остальное не якорится |
| `checkedAt` | время проверки по часам API | когда состояние наблюдалось |
| `writtenAt` | время записи по часам оператора | когда сделана запись |

**Персональных данных нет и быть не может.** Только идентификаторы, счётчики и метки времени:
запись собирается из белого списка полей, а не «из ответа как есть». Содержимое журнала, имена,
адреса и любые тексты сюда не попадают — это условие 152-ФЗ, потому что якорь лежит вне контура,
где данные живут.

### Почему в записи нет `digest` каждого манифеста

Это осознанное решение, а не упрощение. Подмена тела **отдельного** манифеста уже обнаруживается
подписью: `GET /chain` сверяет SHA-256 тела с сохранённым дайджестом и проверяет Ed25519, и при
расхождении вердикт становится `UNPROVEN` — якорь для этого не нужен. А если у противника есть
приватный ключ, он может переподписать и заново заякорить, и сохранённый дайджест ему не помешает.
Единственное, чего подпись не видит, — **удаление**: валидное подмножество остаётся валидным.
Именно это и ловят `chainLength` и `headIds`.

## Первичная настройка (один раз)

```powershell
$env:GH_TOKEN = "<токен с правом создания репозиториев>"
.\tools\setup-anchor-repo.ps1      # создать ПУБЛИЧНЫЙ репозиторий, включить защиту main и ПРОВЕРИТЬ её
git push -u origin main
```

`-Visibility private` создаст приватный, но на бесплатном плане защита в нём не включится —
скрипт скажет об этом отдельным кодом (exit 3), а не общим отказом.

Скрипт не заканчивается словами «защита включена». Он отправляет пробный force-push **в саму
ветку `main`** и требует, чтобы сервер его отклонил: прошёл — значит защиты нет, и это провал
(exit 1), а не «настроено условно». Непроверенная защита ветки защитой не считается.

Проба бьёт именно по `main`, потому что защита настроена на этот ref: пуш в любую другую ветку
никем не защищён и «докажет» отсутствие защиты ложно. Пробный коммит — одиночный (пустое дерево,
без родителей): им нельзя дополнить историю, только перезаписать её. Если защита вдруг отсутствует
и перезапись прошла, скрипт **сразу восстанавливает** `main` на прежний SHA (это возможно как раз
потому, что защиты нет) и печатает SHA для ручного отката.

## Как записывается

```bash
# 1. состояние цепочки (право integrity.summarize, HIGH)
node tools/record-anchor.mjs --api https://family.waibcraft.ru/api/v1 --token "$FP_TOKEN"

# проверить, ничего не записывая
node tools/record-anchor.mjs --api ... --token ... --dry-run

# из сохранённого ответа, без сети (когда токена ещё нет)
node tools/record-anchor.mjs --from summary.json
```

Скрипт отказывается писать запись, если вердикт не `COHERENT` (`EMPTY`, `TOO_LARGE`, `BROKEN`,
`DRIFTED`, `UNPROVEN` — не успех), и если новых голов нет: повторная запись одного и того же
состояния только раздувает журнал и мешает считать покрытие.

После записи — коммит и push в `main`. Дальше запись не меняется никогда.

## Как сверяется

```bash
node tools/verify-anchor.mjs --api https://family.waibcraft.ru/api/v1 --token "$FP_TOKEN"
```

Проверка инструментов (без сети, без git):

```bash
npm test     # 10 тестов: отказ на не-COHERENT, ловля удаления, замены головы, пропуска sequence
```

| Код | Значение |
|---|---|
| 0 | сходится |
| 1 | расхождение — разбирать по выводу |
| 2 | судить нельзя (записей нет, `EMPTY`, `TOO_LARGE`) |

Что проверяется: `manifestCount` не меньше, чем в последней записи; при равном счёте головы те же;
`sequence` без пропусков; текущий вердикт `COHERENT`.

## Чего якорь не даёт

- **Не защищает от того, у кого есть доступ к обоим контурам.** Если якорь можно переписать теми
  же учётными данными, что прод, он защищает только от порчи приложения. **Проверено 2026-10-27:**
  SSH-ключ прод-хоста к этому репозиторию доступа не имеет (`git ls-remote` → `Repository not
  found`), а защищённая `main` отклоняет force-push и удаление включая администраторов.
- **Не заменяет сводку** `GET /chain`: якорь отвечает «не удалили ли», сводка — «сходится ли
  остаток». Нужны обе.
- **Не заменяет церемонию ключа.** Без боевого ключа подпись тестовая.
- **Не работает, если сверку не делают.** Самый вероятный провал — записи есть, никто не смотрит.

## Альтернативный носитель

Тот же формат записи годится для объектного хранилища с Object Lock (Cloudflare R2 или российский
аналог — Yandex Object Storage, VK Cloud, Selectel): один объект `anchors/<sequence>-<checkedAt>.json`
вместо строки JSONL, неизменяемость на стороне сервиса. Меняется транспорт, не формат.
